# Monitoring v3 connector

Use Worker `/v3/monitoring` or app `/api/mcp/v3/monitoring/c/<token>`. Deploy the app's `/api/v3/monitoring/*` routes first; the keyed URL refuses discovery (503) until the Worker answers as `signalbase-monitoring-v3`. Keyed URLs contain credentials and must not appear in logs or reports.

Seven tools manage a team's monitors: `create_monitor`, `list_monitors`, `get_monitor`, `update_monitor`, `add_monitor_targets`, `list_monitor_targets` and `remove_monitor_targets`. Four more manage alerts — saved signal searches that email every new matching signal, with no company list: `create_alert`, `list_alerts`, `get_alert` and `update_alert`. An alert's `filters` are the public search endpoint's own query parameters for its signal type (`departments=people`, `seniorities=head`, `countries=DE`, `round=seed`…), so the natural flow is: run the search tool, review the results, then `create_alert` with the same arguments; the app validates them with the search's parser and reports paging/sort/date parameters back as `ignored`. One signal type and one inbox (`email`, default the account owner's) per alert; each alert sends at most a daily cap of emails, and each email costs 1 credit. Five more cover custom signals — signal types the team defines itself: `create_custom_signal` takes a name and a plain-English rule for what a post about the author's own company must say (optionally `targets`, domains or LinkedIn company URLs, to restrict the sweep to those companies); the app compiles it into search phrases and a matching rule and test-runs it against recent posts, so the definition walks `compiling → testing → ready` over a few minutes. `get_custom_signal` is how the agent polls and reads the test leads; `update_custom_signal` with `active: true` starts it (the test leads become its first signals) and `active: false` pauses it. `list_custom_signal_definitions` returns the shared global catalogue (`stealth_exit`, `new_office`, `founding_hire`, …) together with the team's own definitions, and `search_custom_signals` reads the signals any of them have produced, filtered by slug list, confidence, event date and company. The search is the one paid tool on this profile (1 credit per page of at most 50 rows; `count: true` is free); everything else is free. A custom slug is also a valid `signal_types` entry on a monitor. The custom-signal tools obey the app's rollout switch: while custom signals are admin-only, a key outside the rollout gets a 403 with the reason, not a 404.

They are the first tools in this Worker that write to a customer's account, and the eight that write carry `readOnlyHint: false`. Definitions and execution live in the app, which runs them through the same monitoring procedures as the REST API and the dashboard. This profile only validates arguments and forwards them.

Three things are deliberately absent, and the contract tells the model so rather than leaving it to improvise:

- No tool takes or returns a webhook. Attaching an endpoint mints a signing secret shown exactly once, and a secret must not pass through model context or a transcript. Monitor reads return an allowlisted shape without the webhook block, even for monitors that own one. Webhooks are attached on the Monitoring page or over REST.
- No delete. `update_monitor` / `update_alert` / `update_custom_signal` with `active: false` is the reversible stop; deleting a monitor also deletes its targets, and removing a definition is done on the Custom signals page or over REST.
- No batch larger than 100 targets (REST allows 500). `add_monitor_targets` accepts `dry_run: true`, which reports what the call would add, skip and reject, plus the team's remaining capacity, and writes nothing.

`operation_id` makes writes safe to retry. The app reserves against (team, endpoint, operation_id) before executing, so an identical retry replays the stored result instead of applying the change twice — a lost response to `create_monitor` does not produce a second monitor. After a transport failure, retry the identical call with the same id; a different change needs a new id, and reusing an id with different arguments returns `idempotency_conflict`. The reservation lasts ten minutes and lives in Redis, so a Redis outage fails the call rather than running it unprotected.

The MCP resource `signalbase://monitoring/v3/guide` provides generated concepts (target kinds, resolved vs pending, signal types, the per-type alert filter vocabulary, the custom-signal lifecycle and how to write a rule, limits) and examples.

`src/monitoring_contract.py` is generated by the app's `scripts/export-monitoring-contract.ts` with `MONITORING_WORKER_PATH` pointing at this checkout; run it with `--check` when reviewing paired changes and never hand-edit it. Every call sends the contract hash as `X-Monitoring-Contract`, and the app refuses a mismatched hash before changing anything, so a drifted Worker cannot drive writes against tool definitions the user never saw. `tests/test_monitoring_v3.py` covers discovery, the absent tools, pre-IO validation, operation_id handling and routing.
