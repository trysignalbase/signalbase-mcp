# Monitoring v3 connector

Use Worker `/v3/monitoring` or app `/api/mcp/v3/monitoring/c/<token>`. Deploy the app's `/api/v3/monitoring/*` routes first; the keyed URL refuses discovery (503) until the Worker answers as `signalbase-monitoring-v3`. Keyed URLs contain credentials and must not appear in logs or reports.

Seven tools manage a team's monitors: `create_monitor`, `list_monitors`, `get_monitor`, `update_monitor`, `add_monitor_targets`, `list_monitor_targets` and `remove_monitor_targets`. They are the first tools in this Worker that write to a customer's account, and the four that write carry `readOnlyHint: false`. Definitions and execution live in the app, which runs them through the same monitoring procedures as the REST API and the dashboard. This profile only validates arguments and forwards them.

Three things are deliberately absent, and the contract tells the model so rather than leaving it to improvise:

- No tool takes or returns a webhook. Attaching an endpoint mints a signing secret shown exactly once, and a secret must not pass through model context or a transcript. Monitor reads return an allowlisted shape without the webhook block, even for monitors that own one. Webhooks are attached on the Monitoring page or over REST.
- No delete. `update_monitor` with `active: false` is the reversible stop; deleting a monitor also deletes its targets.
- No batch larger than 100 targets (REST allows 500). `add_monitor_targets` accepts `dry_run: true`, which reports what the call would add, skip and reject, plus the team's remaining capacity, and writes nothing.

`operation_id` makes writes safe to retry. The app reserves against (team, endpoint, operation_id) before executing, so an identical retry replays the stored result instead of applying the change twice — a lost response to `create_monitor` does not produce a second monitor. After a transport failure, retry the identical call with the same id; a different change needs a new id, and reusing an id with different arguments returns `idempotency_conflict`. The reservation lasts ten minutes and lives in Redis, so a Redis outage fails the call rather than running it unprotected.

The MCP resource `signalbase://monitoring/v3/guide` provides generated concepts (target kinds, resolved vs pending, signal types, limits) and examples.

`src/monitoring_contract.py` is generated by the app's `scripts/export-monitoring-contract.ts` with `MONITORING_WORKER_PATH` pointing at this checkout; run it with `--check` when reviewing paired changes and never hand-edit it. Every call sends the contract hash as `X-Monitoring-Contract`, and the app refuses a mismatched hash before changing anything, so a drifted Worker cannot drive writes against tool definitions the user never saw. `tests/test_monitoring_v3.py` covers discovery, the absent tools, pre-IO validation, operation_id handling and routing.
